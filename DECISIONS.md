# Decisions

## 2026-10-02: Area of interest (AOI)

**Decision:** The AOI is a rectangle in British National Grid (EPSG:27700),
easting 488000–585000 and northing 225000–325000 (97 km × 100 km, 9,700 km²).
It covers Cambridgeshire and Peterborough with a margin on every side.

**Why:**
- A simple rectangle is easy to reproduce and to upload to other tools.
- British National Grid uses metres, so the extent and area are exact and
  easy to check.
- The margin means features near the county boundary are not clipped.

**WGS84 copy:** A copy in WGS84 (EPSG:4326) is also kept, for tools that
need latitude and longitude. Before reprojecting, the edges are densified
with a vertex every 1 km. A rectangle in British National Grid is not a
rectangle in latitude/longitude, so reprojecting only the four corners would
make the edges drift from the true boundary. With densified edges the WGS84
copy still measures 9,700 km² when converted back.

**Outputs:** `data/aoi/cambs_aoi.zip` and `data/aoi/cambs_aoi_wgs84.zip`,
generated by `scripts/make_aoi.py`.

## 2026-10-02: Decoding the SSSI Impact Risk Zone code

**Decision:** Each IRZ zone's 13-digit `irzcode` is split into one column per
development category (`irz_all_consultations` … `irz_water_supply`) in
`irz.gpkg`. A value of 0 means the category is not triggered. Higher values
mean fewer developments trigger consultation.

**Why:** The download has no per-category columns, only the code inside
`irzurl`. The digit order and value meanings were confirmed from the IRZ web
tool's own code and its advice templates, and they match the category order
in Appendix 3 of the IRZ User Guidance. Details and worked examples are in
`docs/irz_code_mapping.md`.

**Caveat:** The value meanings are taken from the live templates on
2026-10-02, and Natural England updates the IRZs every two months.

## 2026-10-02: Ancient woodland: revised inventory where it exists

**Decision:** `ancient_woodland.gpkg` uses the revised Ancient Woodland
Inventory wherever it has coverage, and the original inventory only outside
it. Coverage is taken as land within 3 km of a revised wood. Original woods
whose centre lies outside that area are added with `source = "original"`.

**Why:** The revised inventory covers most of the AOI but not all of it.
There are no revised woods in the north-east corner (around Castle Rising,
Congham and Reffley woods), which appears to be West Norfolk, or on part of
the western edge (around Hollington and Thickthorn woods). Original woods
the revision dropped are scattered and mostly within about 1 km of revised
woods. The woods in these two areas are 3–47 km from the nearest revised
wood. Inside coverage, adding original polygons back would bring back woods
the revision deliberately removed.

**Result:** 2,114 revised and 45 original woods (2,159 rows).

**Caveat:** The data has no coverage boundary, so 3 km is a judgement.
County boundaries for the revision projects would give a cleaner line.

## 2026-10-02: Priority habitat slimmed down

**Decision:** `priority_habitat.gpkg` keeps only `uid`, `mainhabs`,
`addhabs`, a recomputed `area_ha` and the geometry. Shapes are simplified
with a 1 m tolerance, keeping their topology, and repaired so they stay
valid.

**Why:** The file was 77.9 MB, over GitHub's 50 MB warning size. It is now
21.5 MB, with vertices cut from 3.69 to 0.86 million and total area changed
by 0.02%. `area_ha` is recomputed because the source `areaha` is the area
before clipping.

**Caveat:** The download has no confidence column, so none is kept.

## 2026-10-02: Short names for storm overflow columns

**Decision:** The EDM spreadsheet headings are renamed to short snake_case
names (for example `spill_count`, `outlet_ngr`). The lookup is
`EDM_COLUMNS` in `scripts/prepare_data.py` and is listed in
`docs/data_dictionary.md`.

**Why:** The original headings are long and contain line breaks and
punctuation, which makes them awkward to use in code and GIS tools. The
script stops with an error if the spreadsheet gains a column the lookup does
not cover, so new columns are not silently mislabelled.

## 2026-10-02: Assurance decision tree

1. Inside SAC / SPA / Ramsar → A3 (may → A4)
2. Inside SSSI → A3 (may → A4)
3. Within 15 m of ancient woodland → A3 (may → A4). Source: Natural England & Forestry Commission standing advice.
4. IRZ All Consultations = 1 or 2 → A3 (may → A4)
5. Abstraction or dewatering = yes, plus any IRZ trigger → A3 (note: groundwater specialist may be needed)
6. IRZ trigger for the work type → A2 (may → A3)
7. Overlaps priority habitat → A2 (may → A3)
8. Nothing found → A1 ('confirm remotely')
9. Intake must collect yes/no for every question; no 'unknown' answers
10. Physical survey required → any A3 becomes A4

Highest level wins; all reasons listed. SSSI condition, European-site linkage and direction of effect are context only and never change the level.

**Note for the build:** these rules must live in one config file
(`app/rules.yaml`), not hard-coded, so they can be changed easily. Nothing
is built yet; this entry records the decision only.

## 2026-10-02: Work type → IRZ triggers

Which IRZ category values count as a trigger for each type of work (rule 6
of the assurance decision tree). Trigger values assume typical water company
scale. To go into `app/rules.yaml` later; nothing is built yet. IRZ columns
and value meanings are in `docs/irz_code_mapping.md`.

| Work type | IRZ category | Trigger values |
|---|---|---|
| Works beyond existing site boundary | All Consultations | 1–4 |
| New pipeline / sewer | Infrastructure | 1 |
| Storm overflow / outfall / works discharge | Discharges | 2–5 |
| Treatment works with combined heat and power | Combustion | 1 |
| Sludge / anaerobic digestion | Composting; Air Pollution | Composting 1–2; Air Pollution 1–4 |
| Storm tank / larger works | Rural Non-Residential | 2 (and 3 if over 1 ha) |
| New or increased abstraction | Water Supply | 1 (⚠️ approximation) |

**Note:** pipe upgrades and refurbishment don't trigger Infrastructure, per
the IRZ guidance (Infrastructure value 1 excludes "upgrades and
refurbishment of existing network").

**Revised 2026-10-02:**
- Pumping stations removed from the Rural Non-Residential row. Most are
  under its 0.2 ha footprint / 1,000 m² floorspace threshold. Storm tanks
  and larger works stay.
- Sludge / anaerobic digestion widened to Air Pollution 1–4, treating AD as
  an industrial process that emits ammonia (cautious reading; values 3–4
  cover industrial processes).

## 2026-10-02: Intake design

**Decision:** The intake collects five answers before screening:

- `work_type`: one of the work types listed in `app/rules.yaml`
- `beyond_site`, `abstraction`, `dewatering`, `physical_survey_required`:
  yes or no

One set of answers applies to all the sites being screened. If the user
describes a work type that isn't supported, they are told so and offered
the closest supported type. The user confirms a summary of the answers
before screening runs.

**How:** `app/intake.py` runs the conversation through `app/llm.py`, which
uses the provider set by `LLM_PROVIDER` in `.env` (`gemini` by default with
`gemini-flash-latest`, or `claude`). The AI fills in answers the user has
already given and asks only for what is missing, one question at a time, in
plain English. Structured output limits the answers to allowed values, and
the AI never suggests an assurance level; the level comes only from
`app/scoring.py`.

## 2026-10-02: API endpoints and example portfolio

**Decision:** The API (`app/main.py`, FastAPI) has three endpoints:

- `POST /intake`: takes the chat history and returns the next intake turn
  (a question, or a summary to confirm).
- `POST /snapshot`: takes the confirmed intake and the sites as lat/long
  GeoJSON (points or polygons), and returns each site's level,
  may_escalate_to, reasons and context, plus a portfolio summary of counts
  per level. Points are buffered by 50 m.
- `GET /sites/examples`: returns the example portfolio.

The example portfolio is all 461 Anglian Water storm overflows in the AOI
(`data/clean/storm_overflows.gpkg`).

**Why:** Three endpoints match the three steps a user takes: describe the
work, screen the sites, and (for a demo) load a ready-made set of sites.
The storm overflows are real assets spread across the whole AOI, so they
exercise every rule. Data layers are loaded once when the app starts, not
per request.

## 2026-10-02: Frontend

**Decision:** The frontend is a single page served by FastAPI at `/`, using
plain HTML, CSS and JavaScript with Leaflet and the Leaflet.markercluster
plugin loaded from a CDN. No React and no build step.

**How it works:** The left panel runs the intake chat (`POST /intake`). When
the intake is complete the user sees a summary with Confirm and Edit
buttons. Confirming loads the example portfolio (`GET /sites/examples`) and
screens it (`POST /snapshot`). Results show counts per level, a "Book a call
with Mozaic" link and the line "Indicative screening from public data, not
a regulatory decision." The map on the right shows the sites clustered and
coloured by level (A1 green, A2 amber, A3 red, A4 purple, not screened
grey), with a site card on click. If `/intake` fails (for example Gemini is
overloaded), a simple form with the five intake fields appears so the demo
still works.

**Why:** One page with no build step is quick to change and easy to host
alongside the API. The work type list for the form comes from
`app/rules.yaml` via the page itself, so the API stays at three endpoints.

## 2026-10-02: Intake AI switched to Claude Sonnet 5.5, with a message cap

**Decision:** The intake chat uses the Anthropic API with
`claude-sonnet-5-5` by default (`LLM_PROVIDER=claude`). Gemini remains
available by setting `LLM_PROVIDER=gemini`. The key is read on the server
from `ANTHROPIC_API_KEY` in `.env` and never reaches the browser.

The answers come back through Anthropic tool calling: one strict tool,
`submit_intake_turn`, whose input schema is the intake schema built from
`app/rules.yaml`, so enum fields can only hold allowed values. Sonnet 5.5
doesn't accept a forced `tool_choice`, so the request uses `auto`, tells the
model to call the tool, and retries once if it answers in text instead.
Effort is `low` because the turns are short, and server-side fallback is on
in case the model declines.

Each browser session may send at most 20 chat messages
(`INTAKE_MESSAGE_CAP`), tracked by a random cookie. Past the cap, `/intake`
returns 429 and the page switches to the five-question form.

**Why:** Gemini's free tier was repeatedly overloaded and then hit its
20-requests-a-day quota, which stopped the chat. The cap limits what one
visitor can spend on the API. Counts are kept in memory, so they reset when
the server restarts; that's acceptable for a demo but would need shared
storage if the app ran on several servers.

## 2026-10-02: How sites are entered

**Decision:** The map starts with no sites, showing only the screened area,
protected sites (SSSI, SAC, SPA, Ramsar) and Impact Risk Zones. Users add
the location of their work in three ways:

1. **Postcode in the chat.** The AI asks for a postcode, or for the user to
   place the site on the map. It only copies postcodes the user typed (the
   code checks each one appears in the user's messages); it never produces
   coordinates. Each postcode is looked up and becomes a draggable pin the
   user must confirm, noted as postcode-level accuracy. A postcode district
   (such as CB7) only zooms the map. If the location is vague ("near Ely"),
   the AI asks again or asks the user to place the site on the map.
2. **Drawing** points, lines (pipelines) or polygons on the map
   (Leaflet-Geoman).
3. **Uploading or pasting coordinates**, as CSV or GeoJSON (below).

The page shows the note "Upload coordinates for the most accurate results."
The chat won't show its summary until at least one site is on the map.

**Coordinate formats:** CSV with a header row and one of `easting,northing`
(British National Grid), `lat,lon`, or `grid_ref` (e.g. TL2709096270);
optional `name`, and `route` to join rows into a line in order. GeoJSON with
points, lines or polygons, in lat/long or British National Grid (detected
from the values). The coordinate system is taken from the column names or
values and checked against plausible ranges; any bad row rejects the whole
upload with row-by-row reasons. British National Grid sites are sent to the
server unconverted (`crs: EPSG:27700`), so the only conversion is the
server's. Limits: 2,000 sites and 5 MB per upload.

## 2026-10-02: Geocoding with postcodes.io, postcodes only

**Decision:** `GET /geocode` looks up full UK postcodes and postcode
districts with postcodes.io (no key needed). Place names are not
geocoded.

**Why:** Postcodes are precise enough to place a pin the user then
confirms or moves, and postcodes.io needs no account. Geocoding place names
well (towns, rivers, roads) needs a gazetteer such as OS Names; that is
listed under "With more time" in the README.

## 2026-10-02: Pipelines scored in sections

**Decision:** Lines are screened as a corridor 15 m either side of the
route, cut into 50 m sections along the centreline (a remainder under 25 m
joins the last section). Each section is scored with the same rules as any
site. Neighbouring sections with the same level and reasons are merged
into stretches, which the map colours by level. The pipeline's overall
level is its highest section, and each reason says where along the route it
applies (e.g. "0.80–0.95 km"). Settings are in `app/rules.yaml` under
`site_geometry`.

- Distances along the route always count the whole route, including parts
  outside the screened area.
- Area-based rules (Rural Non-Residential 3, over 1 ha) use the whole
  route's footprint, so cutting it into sections doesn't switch them off.
- A section can be A4: rule 10 applies to each section.
- One screening can include up to 1,200 sections (about 60 km of route).
  A 50 km route (1,000 sections) screens in about 1.6 seconds.

**Why:** A single level for a long route hides where the problems are.
50 m sections are fine-grained enough to show which stretch crosses a
designated site, and merging matching neighbours keeps the result readable.

## 2026-10-02: Sites partly outside the screened area

**Decision:** The part of a site inside the screened area (the AOI) is
screened; the part outside is shown grey and dashed, with a warning saying
how much wasn't checked, e.g. "3.0 km of this route is outside the screened
area and has not been checked" or "200.0 ha of this site is outside…". This
applies to lines, polygons and the 50 m area around points. A point within
1 m of the area counts as inside, to allow for rounding when converting
coordinates. Sites wholly outside are "not screened".

**Why:** Screening the inside part gives a useful answer for most of the
site, and the warning makes clear what wasn't checked. (This replaces the
earlier rule that sites not wholly inside were not screened at all.)

## 2026-10-02: Storm overflows only for storm overflow work

**Decision:** The 461 example storm overflows appear on the map only when
the work type is storm overflow. Clicking one adds it to the sites, and a
"Use all 461 storm overflows" button adds them all. Changing to another
work type hides them and removes them from the site list.

## 2026-10-02: API grows to five endpoints

**Decision:** The API now has `POST /intake`, `POST /snapshot`,
`GET /geocode`, `GET /layers/{name}` and `GET /sites/examples`. This
replaces the three-endpoint decision above. Other changes:

- `/intake` takes `{history, sites_placed}` and returns the answers known
  so far, plus any postcodes or districts to look up.
- `/snapshot` accepts lines, and a `crs` for the request or per feature
  (`EPSG:4326` or `EPSG:27700`).
- `/layers/protected` and `/layers/irz` serve the background map layers,
  simplified for display and compressed. The risk-zone layer covers the
  whole area, so the map shows only zones that matter: those asking to be
  consulted on all applications, plus, once the work type is known, those
  that trigger for it.

**Why:** Geocoding and the background layers are separate jobs with their
own caching, and keeping them out of `/snapshot` keeps that endpoint about
screening.

## 2026-10-05: Two-screen redesign

**Decision:** The page is now two screens.

1. **Describe the project.** A grey page with "Plan your project around
   nature" at the top and a chat box in the middle. The AI asks the five
   questions, then how the user wants to give the location: uploading
   coordinates (noted as most accurate), a postcode, or drawing on a map.
   Drawing, and checking postcode pins, happens in a map pop-up. The shape
   is set by the work type (`shape` in `app/rules.yaml`: pipes are lines;
   storm overflows, outfalls and abstraction are points; treatment works,
   sludge/AD and storm tanks/larger works are areas), with a "Draw a
   different shape" link. The five-question form remains for when the chat
   isn't available.
2. **Results.** A full map with a side summary. The work is drawn in
   parts, each coloured by its level: a pipe's stretches (with A and B at
   its ends), or the parts of an area, or of a point's 50 m circle, that
   overlap different protected features. Only the protected areas and
   risk zones the work touches are drawn, dimly, each with an explanation
   box saying what it is, why it matters for the project and the level it
   leads to. The side panel lists every part with its level and a one-line
   reason, explains why A1 parts need only a desk check, and gives what
   each level means. Clicking a row highlights the part and the features
   behind it.

**Level meanings** (`level_meanings` in `app/rules.yaml`): A1 nothing found,
a desk check is enough; A2 an ecologist should review from records; A3
specialist assessment, likely with Natural England input; A4 specialist
assessment plus a site survey.

**Parts merge by level.** Neighbouring sections (routes) and pieces (areas)
with the same level merge, and each part lists all its reasons. Merging
only identical reason sets left slivers where protected-site boundaries are
digitised slightly differently. Areas are cut along the edges of every
protected feature they overlap, and each piece is checked using a copy
shrunk by 5 cm, so touching an edge doesn't count as overlapping.

**Reasons point to map features.** Each reason carries `refs` to the
features behind it (`layer:row`), and each result lists those `features`
with their outlines, so the map can show and explain exactly the areas
involved.

**Removed:** the 461 storm overflow examples (kept in the data and used as a
regression set in the tests) and the background map layers. The API is now
`POST /intake`, `POST /snapshot` and `GET /geocode`.

## 2026-10-05: Chat and form as two separate options; a more conversational assistant

**Decision:** The first screen offers two ways to describe a project, chosen
with a switch under the headline: **Chat with the assistant** (the default)
and **Fill in a form**. The form is its own card, not a hidden fallback:
step 1 asks the work type and the four yes/no questions, each with a short
plain-English hint; step 2 is the location (upload coordinates, postcode or
draw). The location tools are shared and move into whichever option is in
use. If the chat isn't available or hits its message cap, the page switches
to the form with a note, carrying over any answers the chat already found.

The assistant's instructions now favour a natural conversation over a
fixed list of questions. It starts from what the user said, asks an open
question when the description is vague (e.g. new sewer or upgrade?), asks
project-specific versions of the yes/no questions ("Will the trench be deep
enough that you'd need to pump out groundwater?"), checks answers it can
infer instead of asking cold, explains terms when asked, and accepts
answers given out of order. The rules are unchanged: answers are only
recorded once the user gives or confirms them, it never produces
coordinates or guesses postcodes, and it never mentions levels.

**Why:** Testing showed the fixed questions read as jargon ("outside the
existing site boundary?") and asked things the description already made
clear. Users who prefer to fill in fields directly get a proper form.

## 2026-10-05: AI report and results assistant

**Decision:** Two AI features on the results screen, alongside the intake
chat:

1. **Report** (`POST /report`, `app/report.py`). Claude writes a short
   report from the screening: headline, overview, findings (each citing the
   parts it covers, e.g. S1.P1), next steps and caveats. It's given only a
   plain-English facts sheet (`app/explain.py`), never raw rule output. The
   code checks every draft: cited parts must exist, any level mentioned must
   match the cited parts, and every part above A1 must be covered. A failed
   draft gets one retry with the problems listed; after that a plain report
   is built from the facts. The report can be downloaded as Markdown.
2. **Results assistant** (`POST /ask`, `app/assistant.py`). Claude answers
   questions using tools that wrap the deterministic screening code:
   `list_parts`, `get_part`, `find_feature` (incl. how much of the route is
   inside a feature), `nearest` (closest SSSI, woodland etc., touched or
   not) and `what_if` (re-screen with changed answers; the code works out
   exactly which stretches change level). Answers cite parts as [S1.P2],
   which the page turns into links that highlight them on the map. Every
   level in an answer is checked against what the tools returned. Claude
   only (multi-step tool use); it can't move or redraw the route.

Both count against the per-session AI message cap. Results tabs: Sections,
Report, Ask.

**Why:** The rules engine makes every screening decision, which keeps
results repeatable and auditable but meant the AI's only job was filling in
five answers, which a form can also do. These features give the AI work
that rules and forms can't: turning results into an actionable report,
and reasoning over the results with the user ("what if we didn't need
dewatering?", "how much of the route is in the Ouse Washes?"). In both, the
AI explains and the deterministic code supplies the facts.

Routes are checked as a 15 m corridor, so "inside" a site can mean the
corridor overlaps while the centreline doesn't. The facts sheet and the
assistant's instructions say so explicitly, after the assistant caught the
ambiguity itself in testing.

## 2026-10-06: Running without an AI key

**Decision:** The app works fully without an AI key, apart from the AI
features, and says so up front instead of failing on first use.

- Empty settings in `.env` count as not set, so a copy of `.env.example`
  works unchanged (`llm.setting`).
- The server works out which AI features have a provider and key
  (`llm.available()`) and passes that to the page. With no key for the
  configured provider, the first screen opens on the form and the chat
  option is disabled. Without a Claude key, the Ask tab shows a note that
  the results assistant needs `ANTHROPIC_API_KEY`, in place of the question
  box.
- `/report` returns the facts-only report when the AI isn't available (no
  key, an outage or the session cap), instead of an error.
- Only AI calls that succeed count against the session cap. A message is
  reserved before the call, so requests sent at the same time can't pass the
  cap, and given back if the call fails.

**Why:** Reviewers may not have a Claude key. Before this, copying
`.env.example` stopped the app from starting, and without a key the chat,
report and assistant each failed only after the user tried them. Failed
calls also used up the cap. The results assistant stays Claude only:
Gemini tool calling would need its own loop, and the free tier's 20
requests a day would allow only a handful of questions.
